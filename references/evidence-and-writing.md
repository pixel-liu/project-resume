# 证据与写作规范

用于建立事实清单、写作和最终校验。示例中的事实只用于说明方法，不代表当前项目具备相应能力。

## 三个独立维度

| 维度 | 可用状态 | 判断方式 |
|---|---|---|
| 实现 | 已实现 / 部分实现 / 仅文档描述 / 无法判断 | 沿实际调用链检查入口、处理逻辑、持久化或外部集成；仅有依赖和接口声明不足以证明实现 |
| 验证 | 本次执行通过 / 已有结果材料 / 用户提供结果 / 未执行验证 | 写清验证对象与范围；构建通过不能代替业务、性能或生产环境验证 |
| 归属 | 用户确认 / 有辅助线索待确认 / 未知 | 用户说明可确立职责；Git 和项目结构只提供线索 |

静态代码能够支持实现机制的描述，不需要为了写简历强制运行项目；但不能据此声称效果已被实测验证。涉及并发、原子性和一致性时，检查事务边界、并发条件、异常与重试路径后再决定表述强度。

## 候选亮点记录

内部分析可使用以下结构，交付时压缩为易读表格：

```text
亮点：
要解决的问题：
具体实现：
可支持的结果或能力：
实现状态：
验证状态与范围：
个人贡献及来源：
证据：文件路径 + 关键符号 + 当前行号，或文档位置/用户说明
限制或待确认：
拟写条目：
```

证据应当能支持整条描述。辅助函数存在但主流程未调用时，不能据此声称该能力已在业务中生效。行号会变化，保留关键符号便于重新定位。用户可见证据链接使用环境支持的文件链接格式；不要在简历正文中加入这些定位信息。

## 指标口径

已有数据优先了解测量对象、环境、数据规模、并发/负载、前后基线、统计方式和来源。只追问会影响当前表述的关键项。

- 单次本地实验不能写成线上长期效果；接口吞吐量不能写成系统整体容量。
- 平均延迟、P95 和 P99 不能互换；理论复杂度改善不能自动换算为耗时下降。
- 涉及“提升/降低 X%”时，须有可比较的基线与结果；单位、负载或测量范围不同则不直接计算。
- 测试未覆盖的边界和故障场景，不能用“彻底解决”“保证不丢失”“杜绝超卖”等绝对表述概括。
- 用户提供了可使用的数据，就注明其来源；不要擅自要求提供敏感日志，也不要把非必要证明变成成稿门槛。

没有数字时，可以描述已实现的流程、支持的场景、消除的具体重复步骤或实际自动化行为。若只知道实现方式，就写清方式和用途，不附会性能收益。

## 条目表达

常用结构：围绕某个具体问题，使用某种实现或设计，形成可证实的能力或结果。不要机械要求每条都包含完整结构；内容短、事实清楚更重要。

- 技术名词需要与实际行动关联；依赖清单不直接转换成“熟练掌握”。
- 同一条保留一个主要亮点；不要把鉴权、缓存、消息队列、部署等不相关工作塞成一句。
- 对技术选择说明已知取舍；用户未说明当时动机时，不代写“经过深入评估后选择”。
- 区分认证与授权、缓存与数据库、异步处理与可靠投递、事务一致性与最终一致性；仅声明项目实际实现的机制。
- 技能栏与项目经历分开处理。用户需要技能栏时，将可由项目证明的使用经验与用户自述熟练程度区分，不自动评定“精通”。

## 表达示例

### 有实际调用，但没有性能数据

已知：商品详情读取先查 Redis，未命中后查库并回填；更新流程会删除对应缓存；用户确认负责该模块。

可写：
> 为商品详情查询实现 Redis 缓存与未命中回源，并在商品更新后失效对应缓存。

不能额外添加：延迟降低 80%、支撑万人并发、解决所有一致性问题。未验证并发更新情形时，不写“保证强一致”。

### 只有依赖和设计文档

已知：依赖文件包含消息队列客户端，设计文档规划异步下单，但业务代码没有生产与消费流程。

处理：在证据清单中记录为仅文档描述；不生成“基于消息队列实现异步下单”的成稿条目。

### 团队项目和二次开发

已知：基础项目已有登录与订单模块；用户只说明自己补充了订单导出。

可写：
> 在既有订单模块中增加按条件导出功能，完成数据筛选与导出文件生成。

不要据此写成“独立设计并开发整个订单系统”。用户明确补充了其他贡献后，再扩大描述范围。

### 数据明确，但范围有限

已知：用户提供同一台本地机器、同一数据集及相同负载下的接口测试结果，优化前平均耗时 200 ms，优化后 120 ms。

若该数据可用于简历，可写：
> 优化某查询接口，在相同本地测试条件下将平均耗时由 200 ms 降至 120 ms。

具体优化动作必须来自实际材料；不能将上述结果改写为“线上延迟降低 40%”，也不能替换为 P95 指标。
